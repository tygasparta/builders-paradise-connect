# Phase 1 — Foundation, access control and organisation

Everything in this phase is built and verified. This document is the setup
runbook plus an honest statement of what is and is not finished.

---

## 1. Apply the database

The Supabase project (`meeqfqagneykgpfbgkgd`) is owned by you, so migrations
have to be applied by someone with access to it. Nothing here drops or
truncates anything, and every statement is re-runnable.

### Option A — Supabase SQL Editor (no tooling needed)

Open **Supabase → SQL Editor** and run these four files **in order**, one at a
time, checking each succeeds before the next:

| # | File | What it creates |
|---|---|---|
| 1 | `supabase/migrations/20260804090000_phase1_core.sql` | Tables, helper functions, audit + row-stamp triggers |
| 2 | `supabase/migrations/20260804090100_phase1_rls.sql` | Row Level Security policies and integrity guards |
| 3 | `supabase/migrations/20260804090200_phase1_rbac_seed.sql` | 151 permissions, 14 roles, role grants, settings row |
| 4 | `supabase/seed/phase1_demo_org.sql` | 3 branches, 10 warehouses, 15 locations *(removable)* |

To get all four as one paste-able file:

```bash
cat supabase/migrations/2026080409*.sql supabase/seed/phase1_demo_org.sql > /tmp/phase1.sql
```

### Option B — Supabase CLI

```bash
supabase link --project-ref meeqfqagneykgpfbgkgd && supabase db push
```

## 2. Create the first administrator

The database deliberately refuses to let anyone grant a role to their **own**
account, and granting roles at all requires `users.roles.assign` — which nobody
holds on a fresh install. That deadlock is intentional; the first admin is
created out of band.

1. **Supabase → Authentication → Users → Add user.** Set a password and tick
   *Auto Confirm User*.
2. Edit the email at the top of `supabase/seed/bootstrap_super_admin.sql`.
3. Run that file in the SQL Editor.

You can now sign in at `/login`.

---

## 3. Regenerate the typed schema (optional but recommended)

`src/integrations/supabase/types.ts` is generated by Lovable and was empty when
the schema did not exist. The app types against `src/lib/database.types.ts`
instead, which is hand-maintained and matches the migrations. Once Lovable
regenerates the real file, the two can be merged — they are written in the same
style on purpose.

---

## 4. Enable user invitations (optional)

Creating auth users needs the service-role key, which must never reach the
browser. It lives only in the Edge Function:

```bash
supabase functions deploy invite-user
```

Until it is deployed, add users through **Supabase → Authentication → Users**.
The Users screen says so rather than showing a button that fails.

## What Phase 1 delivers

**Access control**
- Email/password sign-in, sign-out, forgot password, reset password
- Session restore, protected routes, deep-link back after sign-in
- Failed-login tracking; five failures lock an account for 15 minutes
- Suspended, locked, invited and role-less accounts are refused with a
  specific reason rather than a broken shell
- 14 roles, 151 granular permissions, branch-scoped role assignment

**Security enforced in the database, not the UI**
- RLS on all 12 tables
- `has_permission()` and friends are `SECURITY DEFINER` with a pinned
  `search_path`, so policies cannot recurse or be shadowed
- `audit_logs` has **no** insert, update or delete policy — rows arrive only
  through definer triggers, so the trail cannot be forged or rewritten
- Triggers block: granting yourself a role, changing your own account status
  or lockout counters, and renaming or deleting a system role

**Organisation**
- Branches: create, edit, activate/deactivate (never deleted), one head office
- Warehouses: all seven types including virtual/employee, in-transit, damaged
  and returns; one default per branch; negative stock off by default and
  double-gated by warehouse flag **and** user permission
- Warehouse locations, company settings, document-number prefixes,
  configurable tax rate and fiscal year

**Shell**
- 18-module sidebar, collapsible to icons, nested, permission-filtered
- Branch and warehouse scope selectors that drive the queries
- Global search (⌘K) across screens, branches, warehouses and people
- Audit trail with server-side paging, filters and a field-level diff
- Dashboard showing **only** live counts

## What is deliberately not finished

- **Trading data.** Sales, purchases, gross profit, cash and bank figures do
  not appear on the dashboard because those tables arrive in Phases 2–4.
  Inventing numbers would have been worse than leaving them out.
- **Five legacy screens** (`inventory`, `goods-receiving`, `pos`, `sales`,
  `accounting`) still render the pre-Supabase sample dataset in
  `src/lib/erp-data.ts`. They are now behind authentication and each carries a
  visible "Sample data — not live" notice naming the phase that replaces it.
  They were kept rather than deleted because their layout is the target.
- **Later-phase sidebar entries** are shown with a phase marker and are not
  clickable. No dead links.
- **The logo.** It was not in the repository, so `BrandMark` draws an original
  placeholder. Paste a URL into Settings → Company → Logo URL and it is used
  everywhere, no code change.
- **The accounting/inventory requirements document** was not supplied. The
  schema was built to the specification in the brief; GRN, adjustment and
  posting rules should be checked against that document before Phase 2.

## Verification actually run

| Check | Result |
|---|---|
| `bunx tsc --noEmit` | Clean, under `strict` + `exactOptionalPropertyTypes` + `noUncheckedIndexedAccess` |
| `bunx vitest run` | 29 passed |
| `bun run build` | Succeeds (SSR + client) |
| Sign-in against live Supabase | Round-trip verified; bad credentials produce a readable error |
| Form validation | Empty submit sets `aria-invalid` and shows per-field messages |
| Auth guard | Unauthenticated `/` redirects to `/login` |
| Responsive | Verified at 375px and 1280px |

The tests include a parity check that parses the SQL migration and fails if the
TypeScript permission catalogue and the database seed ever drift apart, plus
assertions that every permission referenced by an RLS policy exists, that all
definer functions pin `search_path`, and that the audit log has no write policy.

**Not run:** the migrations themselves have not been executed — the database is
yours and Lovable's SQL endpoint cannot reach it (`database_not_managed`). Every
runtime claim above was verified against the live project with an empty schema;
claims about table behaviour follow from the SQL and are unverified until you
apply it.
